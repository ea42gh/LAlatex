# Releasing LAlatex

## Versioning

- `Project.toml` is the authoritative package version.
- Release tags must match the package version exactly:
  `1.0.0` -> `v1.0.0`.

## Pre-release verification

Run:

```powershell
julia --project=. -e 'using Pkg; Pkg.test()'
julia --project=docs docs/make.jl
python docs/smoke_notebooks.py
julia --project=. perf/benchmark.jl
```

Confirm:

- CI is green on the release commit.
- Docs are green on the release commit.
- The docs workflow uses the exact `actions/setup-python` interpreter path for
  `JULIA_PYTHONCALL_EXE`.
- Notebook smoke checks pass.
- The benchmark script runs and prints timestamp, Julia version, thread count,
  active project, elapsed time, and allocated bytes.
- The secondary CI OS lanes are green.
- The Docs workflow is green on both the minimum-supported Julia version and
  latest stable Julia.
- Branch protection on `main` requires the CI and Docs checks before merge.

## Backend note

`Backend.backend_usable(...)` is a runtime usability probe, not a static
installation check. For the SymPy backend it may initialize Python and attempt
to import `sympy`. Use `import_sympy()` when you want explicit initialization
or a direct import failure for diagnostics.

## Release steps

1. Update `Project.toml` to the target version and move `CHANGELOG.md`
   entries from `Unreleased` to that version.
2. Commit and push the release-preparation changes.
3. Wait for CI and Docs to complete successfully on `main`.
4. Run the `Register Package` workflow from GitHub Actions. The workflow
   registers the package version from `Project.toml`; do not enter or track a
   separate version value elsewhere.
5. Wait for the JuliaRegistrator pull request against `JuliaRegistries/General`
   to merge.
6. Let TagBot create the matching `vX.Y.Z` tag and GitHub Release. If TagBot
   does not run, create the matching tag and release manually.
7. Replace autogenerated release notes with a curated release summary when
   needed.
